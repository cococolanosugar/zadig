## 2. 关卡逐级穿透审查与断点清单

### Stage 1 · 项目创建与初始化 — 58

**前端**
- `Projects/Wizard.tsx`：`POST /api/aslan/project/products`，payload 含 `product_name`（表单「项目唯一标识」）、`project_name`（显示名）、`product_feature.{basic_facility,deploy_type,create_env_type}`，与 `template.Product` / `ProductFeature` 对齐。
- 失败：非「已存在」错误会 `message.error` 并 `return`，不假跳过；Helm/PM 跳过资源步骤属刻意分流。
- K8s 完成步：串行创建服务 → 环境 → 工作流；部分失败会汇总 `failures` 后仍进项目页。

**断点**
- **P0 · 列表新建缺 `product_name`**：`Projects/index.tsx` → `projectApi.createProject({ project_name, alias, desc })`；后端 `ensureProductTmpl` 要求 `ProductName` 非空（`product.go`）。列表 Modal 与向导契约不一致。
- **P1 · 列表创建失败静默**：`handleCreate` catch 仅 `return false`，无 `message.error`。
- 向导生成工作流仅 `zadig-build` + `zadig-deploy`，**无 approval 阶段**（相对规范书「构建→审批→部署」不完整，见 Stage 5/6）。

### Stage 2 · 应用/服务定义 — 78

**正向**
- `Services/index.tsx`：`POST /api/aslan/service/services?force=true`，含 `yaml` / `variable_yaml` / `visibility` / `source: spock`；保存前调 `validateServiceYaml`。
- `ImportFromRepoModal` / `ImportFromTemplateModal`：preload/load 与模板变量转换有真实 API。
- 默认 YAML 含 `containers` 结构，可供构建 targets / 环境引用。

**断点**
- **P2**：校验端点异常时 `catch` 不阻断保存（可能放过非法 YAML）。
- 服务→构建绑定依赖用户在 Builds 中手工选 `service_module`，向导不会自动建 Build 配置。

### Stage 3 · 环境创建与集群绑定 — 80

**正向**
- `Environments/Wizard.tsx`：K8s/Helm `POST .../environments?type=`，payload 含 `env_name`、`cluster_id`、`namespace`、`services` 二维数组；PM 走 `/init/type/vm`。
- 项目向导环境创建同样带 `cluster_id`、`namespace: ${project}-${env}`、服务清单。
- Renderset：`HelmRendersetDrawer` 对接 `rendersets/*`；全局变量/服务变量在环境页有读写。

**断点**
- **P2**：集群连通性依赖选中已有集群列表，未见独立「连通性探测」按钮（选错集群会在创建时报错，属延后发现）。
- 命名空间多为表单输入/默认拼接，自动创建依赖后端环境初始化，前端无二次确认失败回滚。

### Stage 4 · 打包与编译配置 — 60

**正向**
- `Builds.tsx`：`targets[].{service_name,service_module}`、`pre_build.{res_req:'low', image_id, build_os}`、`scripts`、`repos` 写入；满足规范强调的 `res_req` 防 panic 底线。
- 执行构建：查找含该服务的工作流 → `getWorkflowPreset` → `triggerWorkflow`（正确范式）。

**断点**
- **P1 · 镜像打包字段缺失**：前端 payload **无** `docker_file` / `build_context` / `registry_id`（后端 `models/build.go` 具备这些字段）。无仓库绑定则 Tag/推送规则不完整。
- **P1**：`service_module` 简单等于服务名字符串，未解析 YAML containers 多模块。
- **P2**：未匹配工作流时仅 warning，不引导创建流水线。

### Stage 5 · 工作流 V4 编排与触发 — 55

**正向**
- DAG：`WorkflowCanvas` 支持 `zadig-build` / `zadig-deploy` / `approval` 等 Job 类型。
- 触发：`WorkflowTriggerModal` 拉 `GET /preset/:name`，改 params 后整包 `POST /workflowtask`，取 `task_id`——契约正确。
- `ManualExecModal`：对应运行中 **pause 阶段续跑**（非首次触发），与规范书命名易混淆，但实现真实。

**断点**
- **P0 · 触发成功后深链缺 `/v1`**：
  ```ts
  `/projects/detail/${projectName}/pipelines/custom/${workflowName}/task/${taskId}`
  ```
  路由实际挂在 `/v1/projects/detail/...`；根级 `*` 为诚实 404 → **任务已创建但用户进不了执行页**。
- **P0/P1 · 向导生成 deploy 无法吃构建产物**：
  ```ts
  spec: { service_name, env }  // 无 source:fromjob / job_name
  ```
  对照 `ZadigDeployJobSpec`：`Source`/`JobName` 才是「上游构建镜像」开关。
- **P1 · `JobConfigDrawer` 中 `zadig-deploy` 无「镜像来源 fromjob」表单项**（该 UI 仅出现在 `zadig-vm-deploy` / `custom-deploy`），K8s 黄金路径在编排器层即难配通。
- 规范书期望的「env_name 动态注入」依赖 preset/params 或 deploy.spec.env；TriggerModal 只渲染 workflow params，不单独改写各 Job `env`（若编排时写死环境则运行时难改）。

### Stage 6 · 人工审批门禁 — 70

**正向（对齐真实 L3，纠正规范书示例）**
- 规范书示例 `{ status: "pass"|"reject", approval_id, stage_name }` **与后端不符**。
- 实际 L3：`ApproveRequest{ workflow_name, job_name, task_id, approve: bool, comment }`（`workflow_task_v4.go`）。
- 前端 `workflowApi.approveStage` + `Execution.handleApprove` **正确对齐 L3**。
- 状态识别：`job.type === 'approval'` 且 `wait_for_approval|waiting`；任务级 `wait_for_approval` Tag/面板存在。

**断点**
- **P1 · 无前端 `approval_users` 门控**：任意能进执行页的用户都看到同意/驳回；无权时依赖后端报错（系统管理员对普通 approval 也非一律放行，见 `canSystemAdminApproveJob` 仅 AI Job）。
- **P1 · 无轮询**：`Execution` 仅 mount/`loadTask` 手动刷新，审批通过后卡片不会自动推进到下一 Stage。
- **P2**：向导默认流水线不含 approval，黄金路径「必经审批」需用户手工加 Job。

### Stage 7 · 发布部署到目标 K8s — 52

**正向**
- 执行页 SSE：`/api/logs/sse/v4/workflow/{wf}/{task}/{job}/1000` → `LogViewer`。
- `ServiceDetail`：Pod/镜像/事件/更新镜像弹窗、环境 YAML 与 live kube YAML 可读。
- 后端 deploy 控制器具备 `SourceFromJob` 镜像引用逻辑（前端未配通则后端无输入）。

**断点**
- **P0 · 镜像贯穿断裂**：向导 + `zadig-deploy` 配置 UI 未强制/未提供 `source=fromjob` → 构建产出镜像难以流入部署 Job → K8s Deployment 滚动更新链路在前端配置层中断。
- **P1 · 部署完成后环境/镜像回填无自动联动**：执行成功后不自动跳转 Env/ServiceDetail，也不轮询刷新 Pod 镜像版本；需用户手工打开环境页。
- **P2**：Helm 路径有 `mergeImage`；纯 K8s deploy 更依赖 fromjob/services 结构，UI 表达不足。

## 3. 参数贯穿与数据流闭环矩阵

| 上游输出 | 下游输入 | 预期贯穿字段 | 审计结果 |
| --- | --- | --- | --- |
| 项目创建 | 服务/环境/工作流 | `product_name`（项目 Key） | 向导 ✅；列表 Modal ❌（缺字段） |
| 服务 YAML | 构建 targets | `service_name` / container module | 半通：需手工选服务；module≈服务名 |
| 服务清单 | 环境 `services[][]` | `service_name` + type | 向导/Env Wizard ✅ |
| 构建配置 | 工作流 zadig-build | build 名 / service 绑定 | 弱绑定：靠同名/服务名启发式匹配工作流 |
| 构建产物镜像 | 部署 Job | `source=fromjob` + `job_name` | ❌ 向导未写；K8s deploy UI 未配 |
| 部署 Job | 目标环境 | `env` / `env_name` | 向导写 `env`；Trigger 不单独改写 Job.env |
| 审批 Job | 继续执行 | `approve` bool + `job_name` + `task_id` | API ✅；默认流水线常无此 Job |
| 部署完成 | Env/Pod 镜像 | 新 image tag | 需手工打开 ServiceDetail；无自动刷新 ❌ |
| 触发任务 | 执行页 | `task_id` 路由 | 有 task_id，但跳转 URL 缺 `/v1` ❌ |

**闭环一句话**：项目（向导）→服务→环境 段较完整；**构建→部署镜像** 与 **触发→执行页路由** 两处硬断点使「发布到 K8s」黄金终态无法保证。

## 5. 优化整改建议与端到端贯通保障

### 立即（打通 P0）

1. **`projectApi.createProject`**：映射为 `{ product_name: project_name, project_name: alias || project_name, desc, product_feature: {...} }`；失败 `message.error`。
2. **`WorkflowTriggerModal` navigate**：改为  
   `/v1/projects/detail/${projectName}/pipelines/custom/${workflowName}/${taskId}`  
   （与 router `pipelines/custom/:name/:taskId` 一致）。
3. **向导默认流水线**：deploy.spec 增加 `source: 'fromjob'`, `job_name: 'build'`, `deploy_contents: ['image']`；可选插入 `approval` Stage。
4. **`JobConfigDrawer` zadig-deploy**：补齐与 vm-deploy 同级的「镜像来源 runtime/fromjob + 上游 Job 名」。

### 本迭代（P1）

5. Builds 表单暴露 `docker_file`、`registry_id`、构建上下文；保存进 payload。  
6. Execution：运行中/待审批状态 `setInterval` 轮询 `getWorkflowTask`；审批按钮按当前用户 ∈ approval_users（或等后端 403）禁用并提示。  
7. 部署 `passed` 后提供「查看环境服务」深链，并在 ServiceDetail 进入时强制刷新 Pod/镜像。

### 回归用例（建议后续实机）

| # | 步骤 | 期望 |
| --- | --- | --- |
| 1 | 列表 Modal 新建项目 | 201/成功，非 empty product name |
| 2 | 向导 K8s 全流程 | 项目+服务+环境+含 fromjob 的工作流 |
| 3 | 配 Build（registry+dockerfile）并绑定服务 | 配置可读回 |
| 4 | TriggerModal 启动 | 进入 `/v1/.../pipelines/custom/.../:taskId` |
| 5 | 审批通过 | 后端放行且 UI 自动进入部署 Stage |
| 6 | 部署成功 | Env ServiceDetail 镜像 tag = 本次构建产物 |

## 6. 结论

E2E 黄金路径综合约 **65/100**：前半段（向导项目/服务/环境）可用性尚可，**后半段「编译产物→审批→K8s 部署回填」参数链未真正贯穿**。优先修复列表建项契约、触发深链、以及 `zadig-deploy`/`fromjob` 镜像贯通，否则无法对外承诺「一条龙发布到目标集群」闭环。
