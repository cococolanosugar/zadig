## 2. 真实缺陷 / 缺失清单（A 类）

### P0 / 高优 P1

#### R1-A1 · 服务删除能力完全缺失（A · P0）

- **现象**：`pages/Services/` 全文无「删除服务」操作、无 `Popconfirm` 删除服务；`api/service.ts` **未封装** `DELETE /api/aslan/service/services/:name/:type`。
- **L3 契约**：`router.go:56` `k8s.DELETE("/:name/:type", DeleteServiceTemplate)`；`service.go:633+` 要求 `projectName`、`production` query，并做 Delete 权限与生产 License 校验。
- **影响**：用户无法在新前端移除错误或废弃服务，CRUD 不闭环。
- **建议**：
  1. `serviceApi.deleteService(name, type, projectName, production)`；
  2. 服务列表行操作或详情工具栏加危险按钮 + `feedback.modal.confirm` / `Popconfirm`；
  3. 成功后刷新列表并清空选中态。

### P1

#### R1-A2 · 服务标签 API 全未接线（A · P1，对应全量报告 P2-2）

| 方法 | 路径 | UI 引用 |
| --- | --- | --- |
| `getServiceLabels` | `GET /api/aslan/service/labels` | **DEAD** |
| `createServiceLabel` | `POST /api/aslan/service/labels` | **DEAD** |
| `updateServiceLabel` | `PUT /api/aslan/service/labels/:id` | **DEAD** |
| `deleteServiceLabel` | `DELETE /api/aslan/service/labels/:id` | **DEAD** |

- **L3**：`addServiceLabelReq` 仅 `label_id/project_key/service_name/production/value`（`service.go:1037-1043`）；前端 `createServiceLabel` 已正确剥离无用的 `key`，契约本身可用。
- **建议**：服务详情侧栏或 Tags 编辑区接线；创建前需先有系统标签定义（`/api/aslan/system/labels`）。

#### R1-A3 · 主机部署（build/deploy）API 未接线（A · P1）

- `getVmServiceDeploy` / `saveVmServiceDeploy` / `getServiceModuleDeploy` → **DEAD**。
- **L3**：属 `build` 域 `/api/aslan/build/deploy*`，与 PM 服务运行配置互补；`PmServiceModal` 仅覆盖 `service/pm` 模板与探活，**不含**部署脚本/模块绑定。
- **建议**：在 PM 服务编辑流中增加「部署配置」页签，或明确产品裁剪并删除死 API。

#### R1-A4 · API 静默吞错残留（A · P1）

`api/service.ts` 仍有 5 处：

| 行号 | 方法 | 行为 |
| ---: | --- | --- |
| 320 | `getCodehostNamespaces` | `catch → []` |
| 337 | `getCodehostRepos` | `catch → []` |
| 353 | `getCodehostBranches` | `catch → []` |
| 406 | `getYamlTemplates` | `catch → []` |
| 418 | `getYamlTemplateDetail` | `catch → null` |

- **影响**：代码库导入/模板导入时，代码源故障会显示「无仓库/无模板」，与真空态混淆（`ImportFromRepoModal` / `ImportFromTemplateModal` 下拉变空）。
- **建议**：附属下拉失败时向上抛或返回 `{ ok:false, error }`，UI 用 `message.error` + 重试；勿默认 `[]`。

#### R1-A5 · 详情 / 版本历史失败通道偏弱（A · P1/P2 边界）

- `index.tsx:220-221` `loadServiceDetail` catch 仅 `setServiceDetail(null)`，**无错误提示**。
- `index.tsx:315-316` `loadVersions` catch → `[]`，无提示（抽屉可能显示「暂无历史版本」假空）。
- **建议**：与列表加载一致，至少 `feedback.message.error`；版本抽屉加 Alert+重试。

### P2

#### R1-A6 · `updateHelmService` 死代码（A · P2）

- `serviceApi.updateHelmService`（`PUT /helm/services`）已定义，**无任何页面调用**；抽屉仅 `createHelmService` / bulk。
- **建议**：Helm 编辑场景接线 PUT，或待产品确认后删除死方法以免台账虚高。

#### R1-A7 · Harbor Chart 浏览 API 未封装（A · P2）

- L3：`harbor.GET /project`、`…/charts`、`…/versions`、`…/version/:version`。
- 前端 Helm「chartRepo」依赖手填 chart 名/版本，无 Harbor 项目级联。
- **建议**：按需补 `serviceApi.listHarbor*` 与级联 Select（非阻塞主路径）。

#### R1-A8 · 版本 API 未收拢进 `serviceApi`（A · P2 / 可维护性）

- `version` 四接口在 `index.tsx` 内联 `http.get/post`，与模块封装风格不一致，易漏 `skipErrorHandler` 策略统一。
- **建议**：迁入 `serviceApi.listServiceVersions / diff / getRevision / rollback`。

#### R1-A9 · 创建空白服务 URL 未带 `projectName` query（C 倾向 / 低风险）

- `index.tsx:434`：`POST /services?production=&force=true`，项目名仅在 body `product_name`。
- **L3**：`CreateServiceTemplate` 授权与落库均用 `args.ProductName`，**不依赖** query `projectName` → 功能正确。
- **建议**：可选对齐保存路径，补 `projectName=` 便于网关审计与日志一致（非功能性缺陷）。

### 4.2 导入流程与 Loader 契约

`ImportFromRepoModal` → `preload` body（`repo_name/branch_name/repo_owner/paths`）与 `PreloadServiceTemplateReq` 一致；`load/sync` query 含 `projectName/repoName/branchName/repoOwner/namespace/production`，与 `loader.go` 读取项一致。`namespace` 默认回落 `repoOwner` 与后端一致。  
同步模式强制单 `service_paths` 元素，符合注释约束。
