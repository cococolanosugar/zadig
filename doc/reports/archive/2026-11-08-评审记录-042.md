## 1. 审查背景与穿透核查成果

本轮为用户指示的「十轮全流程逆向交叉循环特战」第二轮（Loop 02），聚焦环境休眠与唤醒生命周期、全局变量渲染与多服务级联更新、子环境/灰度环境生命周期以及外置集群 Agent 接入脚本生成四大链路。

ZCode 作为独立只读审计员，深入后端 `pkg/microservice/aslan/core/environment/`、`pkg/microservice/aslan/core/multicluster/` 以及官方产物 `zadig-ee-portal/`，核对了环境与集群全量模型，确证基础 A 类契约（休眠唤醒、子环境隔离、集群增删改查）均已闭环（A 类缺口为 0），同时发掘出 3 项关键稳健性与体验缺口：
- **LOOP2-B1 (B 类 · 防呆控制)**：当环境处于休眠态（`status === "Sleeping"`）时，由于后端底层 Pod 已被缩容至 0，此时触发服务副本伸缩、服务配置更新、全局变量保存或 Pod 重启操作均会失败。前端在 UI 层面未作置灰与 Tooltip 解释，且在 Handler 层面缺少前置拦截。
- **LOOP2-B2 (B 类 · 核心体验完整性)**：后端 `multicluster/handler/clusters.go:499,592` 提供了 Agent 接入凭证与脚本生成端点（`POST /api/aslan/cluster/agent/:id/agent.yaml/token`），返回短期 Token 与一键部署脚本命令（`kubectl apply -f ...`）。前端虽然支持选择 `type: agent`，但在创建时强制校验 KubeConfig，且列表无「获取接入脚本」快捷操作，导致 Agent 集群无法闭环上线。
- **LOOP2-C1 (C 类 · 资源回收预警)**：环境模型包含 `recycle_day` 字段。当租约即将到期（剩余 ≤3 天）时，缺乏显式高亮警示提示，用户易因环境被后端 Cron 自动清理而错失延期或数据备份时机。
