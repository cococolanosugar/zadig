## 1. 审查背景与对账结论

本轮对测试中心与质量门禁四条链路做"模型字段 → 前端消费"逐项对账。

**对账总判定**：
- **发现 1 项 A 类伪实现（LOOP5-A1 扫描漏洞统计无真实数据源）**：前端完整渲染漏洞分级统计，但字段 `quality_metrics` 后端不存在，真实数据源 `sonar_metrics`（任务详情已返回）前端零消费 —— 所有漏洞指标恒为 0/85 假数据；
- **发现 2 项 B 类（质量门禁配置未接线）**：测试域 `threshold` 与扫描域 `check_quality_gate` 后端建模完整，前端均未提供配置入口；
- 测试配置多代码仓、Junit 报告解析两条链路对齐良好（C 类增强各 1）。

## 2. 四大穿透核查点结论

### 审查点 1：自动化测试配置与多代码仓拉取 — ✅ 主链对齐（1 项 C 类）

- 多代码仓绑定 ✓：`handleSaveTest`（Quality:705-711）组装 `repos[{repo_name, branch, checkout_path}]`，与后端 `Testing.Repos []*types.Repository`（testing.go）逐字段对齐；
- 运行环境 ✓：`pre_test{build_os:'focal', envs, image_id}`（:733-736）对齐 `Testing.PreTest/ImageID`；前置脚本 `script_type/scripts` ✓；超时 timeout ✓；
- **C-1（PR/Commit/Tag 动态获取）**：测试表单 repos 仅支持 branch 静态绑定；后端 codehost 域 `branches/prs/tags` 端点（code/handler/router.go）与前端 API 均已存在，但测试表单未提供 PR/Tag 切换（与构建表单同等水平）。建议：复用构建模块的代码源联动组件（非阻断）。

### 审查点 2：测试执行结果与 Junit 报告解析 — ✅ 闭环

- 执行统计 ✓：`JUnitSuite{tests, failures, errors, skips, time, testcase[]}`（Quality:308-316）渲染用例总数/失败/错误/跳过/耗时（:2086-2093 失败 Tag）；
- 报告提取 ✓：JUnit XML 经 `GET /testtask/report`（:434）、HTML 报告 `GET /testtask/html/testing/...`（路由 :29）+ workflowv4 变体（:30），前端三 Tab（overview/junit/html，:326）切换渲染；失败用例堆栈展开（`failure._content`/`error._content` 结构已在 JUnitCase 建模，Execution:240 同契约）；
- itreport 本地套件 ✓（itreport 组 4 端点对齐 workflow.ts:1009-1014）。

### 审查点 3：代码扫描任务与漏洞分级统计 — 🔴 A 类伪实现

**后端真实契约**：
- 扫描任务详情 `GET /:id/task/:scan_id` 返回 `ScanningTaskDetail{..., sonar_metrics: {QualityGateStatus, Bugs, Vulnerabilities, CodeSmells, Ncloc, Coverage}, result_link, check...}`（service/types.go:223-235 + scanning.go:627 `SonarMetrics: sonarMetrics`）—— Sonar 类型扫描的真实漏洞分级数据由 `StepSonarGetMetrics` 步骤采集（scanning.go:571-599）；
- 扫描模型含质量门禁开关 `CheckQualityGate`（models/scanning.go:51，service :141 消费）。

**前端断裂点（A 类证据）**：
1. `Scanners.tsx:158-164` 定义 `quality_metrics{bugs, vulnerabilities, code_smells, coverage, ai_suggestions}` 并完整渲染（:781「阻断漏洞数」、:1564-1585 四 Statistic）——但后端 `models.Scanning` 与列表/详情 API **均无 `quality_metrics` 字段**（pkg 全量 grep 零命中）→ 所有统计**恒为 0**；
2. `coverage ?? 85`（:1585）为**硬编码假覆盖率兜底**，与测试中心 R6 轮修复的"假 100%"同性质；
3. 真实数据源 `sonar_metrics`（任务详情已返回）**前端零消费**（grep 零命中）；
4. 后端字段为 string 类型（Sonar 原始指标），前端按 number 渲染——接线时需 Number() 转换。

**修复方案（LOOP5-A1）**：
1. 打开扫描任务详情（`openScannerDetail` 拉取 `GET /:id/task/:scan_id` 最新任务）时，从 `detail.sonar_metrics` 读取真实指标（`Number(metrics.Bugs)` 转换）填充统计卡片；
2. 删除 `quality_metrics ?? 0` 与 `coverage ?? 85` 假兜底，无数据展示 `-`；
3. 漏洞分级（Blocker/Critical/Major/Minor）后端 SonarMetrics 未拆分级别（仅 bugs/vulnerabilities 聚合），如需分级需后端扩展 sonar facets 查询——建议保持聚合口径，卡片文案改"漏洞缺陷/安全风险"与后端字段一一对应。

### 审查点 4：质量门禁拦截与工作流联动 — ⚠️ 2 项 B 类配置缺口

- **LOOP5-B1（扫描质量门禁开关未接线）**：后端 `models.Scanning.CheckQualityGate`（:51）+ service :141（`if args.CheckQualityGate`）承载"Sonar 质量门禁不过则扫描任务失败"的阻断逻辑；前端 Scanners 创建/编辑表单**未提供该开关**，且 `:588` 创建 payload 硬编码 `check_quality_gate: false` → 门禁阻断能力整体不可用。**建议**：表单增加 Switch（sonar 类型时显示），payload 透传真实值；
- **LOOP5-B2（测试通过率阈值不可配置）**：后端 `Testing.Threshold`/`JUnitTestResultPassRate`/`TestResultPath`（testing.go）承载"通过率阈值门禁"；前端创建表单仅 `initialValues` 固定 `junit_test_result_pass_rate: 100`（:601）且**无 threshold 表单项**（grep 表单零命中）。**建议**：表单增加「通过率阈值 (%)」InputNumber（0-100，联动 test_result_path），payload 透传；
- 工作流联动 ✓：`zadig-test` Job 经 `test_name` 引用测试配置（JobConfigDrawer test 分支），门禁失败阻断由后端 threshold/CheckQualityGate 判定——前端缺配置入口即本轮 B 类主因；
- 审批联动 ✓：approval Job + wait_for_approval 门控（R2/Loop3 已核）。

## 4. 总结

1. **测试执行/报告链路（审查点 2）与测试配置主链（审查点 1）对齐良好**；Loop 06 轮的取消/重启/产物下载修复经本轮复验保持生效；
2. **唯一 A 类（LOOP5-A1）为"有渲染、无数据源"的伪实现**——与 R6 轮修复的"假 100% 指标"同根性（假兜底掩盖缺数据），修复方向一致：真实数据源（sonar_metrics）驱动 + 删除假兜底；
3. 质量门禁后端建模完整（threshold/CheckQualityGate），但**两端配置入口均缺失**（B1/B2），导致门禁能力整体空转——建议与 A1 同批修复（同属 Scanners/Quality 两文件）；
4. 漏洞五级分级需后端 Sonar facets 扩展，当前以聚合口径对齐（C2 记录）。
