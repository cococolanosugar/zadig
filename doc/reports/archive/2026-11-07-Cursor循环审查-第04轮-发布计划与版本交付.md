## 2. A 类真实缺陷清单

### P0

#### R4-A1 · 发布计划执行 / 审批 / 复制控制面全缺（A · P0）

- **L3**（`release_plan/handler/router.go:28,39-44`）：
  - `POST /v1/:id/execute` → `ExecuteReleaseJob`
  - `POST /v1/:id/retry` → `RetryReleaseJob`
  - `POST /v1/:id/skip` → `SkipReleaseJob`
  - `POST /v1/:id/schedule_execute` → `ScheduleExecuteReleasePlan`
  - `POST /v1/:id/approve` → `ApproveReleasePlan`
  - `POST /v1/:id/status/:status` → `UpdateReleaseJobStatus`
  - `POST /v1/:id/copy` → `CopyReleasePlan`
- **前端**：`releasePlan.ts` 仅 `getPlans/createPlan/deletePlan/getHookSettings/updateHookSettings`；`ReleasePlan/index.tsx` **无**执行、重试、跳过、审批、定时执行、状态更新、复制任何按钮/调用
- **影响**：发布计划无法完成官方核心闭环，页面仅日历式 CRUD + Hook
- **建议**：在 `releasePlanApi` 补齐上述方法；详情抽屉按 Job 状态渲染操作区，对齐 EE `/v1/releasePlan/detail`

#### R4-A2 · 详情抽屉硬编码假里程碑，未拉真实计划 / Job（A · P0）

- **位置**：`ReleasePlan/index.tsx:428-453`（「代码审查门禁已通过 / 回归 100% / 待主管签批」写死）
- **L3 应对**：`GET /v1/:id`、`GET /v1/:id/job/:jobID`；打开抽屉应拉详情而非仅用列表行
- **影响**：对用户呈现虚假合规状态，属于功能性伪装数据
- **建议**：删除假 Checklist；接入 `GetReleasePlan` + Job 列表/详情；审批态走真实 `approve`

#### R4-A3 · 批量部署：幻觉路由 + catch 假成功（A · P0）

- **位置**：`Delivery/index.tsx:340-359`
  ```ts
  await http.post(`/api/aslan/delivery/releases/${id}/deploy?projectName=...&envName=...`, {}, { skipErrorHandler: true });
  // catch { feedback.message.success(...批量部署任务！) }
  ```
- **L3**：`delivery/handler/router.go` **不存在** `POST /releases/:id/deploy`（无 Deploy 处理器）
- **影响**：请求必然失败，但 UI **仍提示成功**并关闭 Modal——比静默更危险
- **建议**：立刻改为 `message.error`；确认 EE 真实部署路径（多为工作流/环境部署，而非该伪路由）后重接或移除入口

#### R4-A5 · 制品 Lineage Drawer 为装饰 Timeline，非契约溯源（A · P1）

- **位置**：`Delivery/index.tsx:742-793` 四级 Timeline 文案写死（「Harbor CVE 扫描」「qa/预发」等）
- **L3**：`GET /artifacts`、`GET /artifacts/:id`、`GET /artifacts/image`（`GetDeliveryArtifactIDByImage`）——前端 **无** image 查询封装，Drawer **未**按 activities/镜像 ID 拉链路
- **建议**：按 artifact id / image 拉详情与 activities；去掉营销式假步骤

#### R4-A6 · `releasePlanApi.getPlans` 模式性吞错（A · P1）

- **位置**：`releasePlan.ts:28-30` `catch { return []; }`
- **连带**：页面 `fetchPlans` 虽有外层 catch，但 API 已吞掉异常 → 外层 **永远成功空表**，用户以为「无计划」
- **建议**：去掉 API 内吞错；失败抛出，由页面 `feedback.message.error`

#### R4-A7 · 交付版本删除未暴露 UI；Labels API 死代码（A · P1）

- **L3**：`DELETE /releases/:id`、`GET /releases/labels`
- **现状**：`deliveryApi.deleteDeliveryVersion` / `listDeliveryLabels` **已封装但页面零调用**（labels 全仓仅定义处命中）
- **建议**：版本行增加删除二次确认；创建表单/筛选接入 labels

#### R4-A8 · `RetryDeliveryVersion` 未入 API 层（A · P1/P2 边界）

- **现状**：`Delivery/index.tsx:255-268` 直接 `http.post('/api/aslan/delivery/releases/retry?...')`，功能可用
- **建议**：下沉为 `deliveryApi.retryDeliveryVersion(id, projectName)`，与 create/check 一致；失败态按钮可按 `status===failed` 强调
