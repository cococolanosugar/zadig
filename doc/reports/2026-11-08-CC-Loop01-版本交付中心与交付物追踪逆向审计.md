## 二、P0 级 Gap（阻断主流程 / 伪造事实）

### P0-1 失败发布“重试”契约错误：body 传参，后端只读 query → 100% 失败

- 前端：`frontend/src/api/delivery.ts:170-172`
  ```ts
  async retryDeliveryVersion(payload: { id: string; project_name: string }) {
    return http.post('/api/aslan/delivery/releases/retry', payload, { skipErrorHandler: true });
  }
  ```
- 后端：`pkg/microservice/aslan/core/delivery/handler/version.go:329-339`
  ```go
  projectName := c.Query("projectName")   // body 完全被忽略
  id := c.Query("id")
  ```
- 真理源：`94.*.js` 中官方定义 `POST /api/aslan/delivery/releases/retry?projectName=<p>&id=<id>`，无 body。
- 影响：任何“重试交付”都会返回 400 `projectName can't be empty`，失败版本无法恢复。
- 修复：`retryDeliveryVersion(id, projectName)` 改为 query 传参；`Delivery/index.tsx:267` 同步调用。

### P0-2 Helm 版本创建缺少 `image_registry_id`，后端硬性拒绝

- 前端：`CreateHelmReleaseModal.tsx:214-222` 组装的 payload 只有 `version/project_name/desc/labels/chart_repo_name/original_chart_repo_name/services`。
- 后端：`delivery/service/version_v2.go:610-612`
  ```go
  if len(args.ImageRegistryID) == 0 {
      return e.ErrCreateDeliveryVersion.AddDesc("image registry not appointed")
  }
  ```
- 真理源：官方创建组件调用 `getRegistryWhenBuildAPI(project_name)`（`GET /api/aslan/system/registry/project?projectName=`）填充 `imageRegistryList`，并强制 `image_registry_id`；`changeImageRegistry` 会按仓库前缀重写 `target_image`。
- 影响：Helm 版本创建**永远失败**，当前弹窗是死表单。
- 修复：新增仓库选择（项目维度），payload 增加 `image_registry_id`；同步补 `services[].images[]`（含 `push_image`、`target_image_tag/source_image_tag`），否则即使创建成功也不会分发镜像。

### P0-3 Chart 版本接口响应被误当作字符串数组解析

- 前端类型：`frontend/src/api/delivery.ts:132-140` 声明 `Promise<string[] | string>`。

  const res = await deliveryApi.getChartVersionFromRepo(item.chart_name, chartRepoName);

  if (Array.isArray(res) && res.length > 0) latestVersion = res[0]; // ← 实际是对象

- 影响：`chart_version` 被写成 `[object Object]`，React 输入框异常，提交时 JSON 序列化为对象导致后端反序列化失败。

### P0-4 交付物列表字段契约错位 + 假数据兜底

- 前端假定字段：`Delivery/index.tsx:55-68`（`project_name/workflow_name/size/created_at/commit_id/branch/author`）与列定义 `:411-465`。

## 三、P1 级 Gap

### P1-1 版本类型枚举错配，Helm 标识与下载入口失效
- 后端真实值：`setting.DeliveryVersionTypeYaml = "K8SYaml"`、`DeliveryVersionTypeChart = "HelmChart"`（`pkg/setting/consts.go:332-333`）。
- 前端比较：`Delivery/index.tsx:497` `record.type === 'helm' ? <Tag>Helm</Tag> : <Tag>K8s</Tag>`；`:579` 下载按钮同样用 `'helm'` 判定。
- 附加：版本列表接口固定排除 `services`（`version_v2.go:1363-1364`），故 `record.services` 恒为空，下载按钮的第二个条件也恒假。
- 影响：所有 Helm 版本都显示为 K8s，列表页“下载 Chart”按钮永不出现。
- 修复：按 `HelmChart` 判定；列表行单独提供下载入口（调用详情或后端提供 chart 列表）。

### P1-2 K8s 创建伪造 Chart 字段，详情页出现假 Chart 清单
- 前端：`Delivery/index.tsx:367-378` 对 K8s 版本写入 `chart_name: s.service_name`、`chart_version: values.version`。
- 后端 K8s 版本不使用 chart 字段（`CreateK8SDeliveryVersionV2` 只处理镜像与 yaml）。
- 详情页：`:917-971` 以 `services.some(s => s.chart_name)` 展示“Chart 清单”并提供下载 → 对 K8s 版本会出现假 Chart 并下载失败。
- 修复：K8s 创建不写 chart 字段；详情按 `type === "HelmChart"` 展示 Chart 清单。

### P1-3 版本唯一性预检被吞掉（且 K8s 创建无预检）
- `CreateHelmReleaseModal.tsx:207-212`：
  ```ts
  try { await deliveryApi.checkDeliveryVersion(...) } catch { /* 如果校验不通过，提示可能重复 */ }
  ```
  注释说要提示，实际什么也没做，直接继续创建。
- 真理源：官方把它实现为 Form `validator`，重复时抛 “versionNameExists” 阻断提交。
- 修复：改为表单异步校验或提交前 `await` 并在失败时 `feedback.message.error` + `return`；K8s 创建表单同样接入。

### P1-4 Helm 全局变量合并回写覆盖，丢失 chart/images 字段
- 后端：`version_v2.go:1508-1521` 只返回 `{services:[{service_name, yaml_content}]}`。
- 前端：`CreateHelmReleaseModal.tsx:148-157` 直接 `setServices(res.services)`，`chart_name/chart_version/images` 全被清空。
- 后果：点击“合并应用全局变量”后再提交，必然被 `:197-203` 的完整性校验拦截，用户需重新填写全部 Chart 信息。
- 修复：按 `service_name` 合并 `yaml_content`，保留其余字段；或后端返回完整 service 结构。

### P1-5 版本列表未按项目/分页/标签查询，labels 接口未接线
- 前端：`delivery.ts:73-77` 仅可选 `projectName`，`Delivery/index.tsx:290` 无参调用 → 全租户列表。
- 后端：`ListDeliveryVersionV2Args` 支持 `projectName/page/per_page/label/workflowName/taskId`（`version_v2.go:1343-1352`）。
- 真理源：官方固定传 `projectName&page&per_page=200&label=`。
- 影响：项目成员（仅有项目级 `Version.View`）会因缺少 `projectName` 被要求系统级 `DeliveryCenter.ViewVersion` 而 403；标签筛选完全缺失；`listDeliveryLabels`（`delivery.ts:94`）零调用。
- 修复：从路由/项目 store 取项目名传入；增加分页与标签筛选；渲染 `labels`。

### P1-6 交付物列表未接过滤/分页；后端 repo/branch 分支丢弃其它过滤条件
- 前端：`Delivery/index.tsx:285` 裸请求 `/api/aslan/delivery/artifacts`，无 `type/image/name/imageTag/repoName/branch/per_page/page`；搜索仅前端按 name/project/workflow（后两者恒空）。
- 后端 Handler 支持：`type/image/name/imageTag/repoName/branch/source`（`handler/artifact.go:51-58`）。
- 后端缺陷：当 `RepoName/Branch` 非空时，`delivery/service/artifact.go:63-87` 只按 activity 查询，**完全忽略** `Type/Image/Name/Source` 过滤；且同一 artifact 命中多条 build activity 时会重复返回（未去重）。
- 另：`X-Total` 头部在 `frontend/src/api/client.ts:57-61` 被拦截器丢弃，服务端分页无总数可用。
- 修复：前端补筛选栏（service_name/type/image/repo/branch）与分页；后端在 service 层对合并后的查询统一应用全部过滤并去重；拦截器暴露 headers 或提供专用方法。

### P1-7 Chart 下载：二进制被当 JSON 解析 + 回退 token 键错误
- `delivery.ts:147` `{ responseType: 'blob' as unknown as undefined }`：运行时就是 `undefined`，axios 按 JSON 解析 octet-stream → `.tar.gz` 内容损坏。
- `delivery.ts:160` 回退用 `localStorage.getItem('token')`，但鉴权态存于 zustand `zadig_auth_store`（`stores/auth.ts:115`、`client.ts:31-45`），该键不存在 → 直链无 token → 401。
- 修复：`responseType: 'blob'`；token 取 `useAuthStore.getState().token`；失败时给出明确错误而非静默 `window.open`。

### P1-8 “批量发布到环境”是无操作假交互
- `Delivery/index.tsx:349-360`：仅弹一条 info 后关闭；`:1149-1182` 弹窗却声称“将把全部服务镜像批量分发部署至目标集群环境”，后端无 `/releases/:id/deploy` 路由。
- 影响：误导用户以为已下发部署。
- 修复：移除按钮，或改为“前往发布计划/工作流”真实跳转，并在弹窗文案中明确“当前仅支持经工作流编排下发”。

### P1-9 “重试交付”对任意状态可见，后端仅允许 failed
- 前端：`:564-578` 无条件渲染。
- 后端：`version_v2.go:579-581` `RetryCreateHelm...` 对非 failed 返回 “can't reCreate version with status”。K8s 重试（`RetryCreateK8SDeliveryVersionV2:386`）同样有状态校验。
- 修复：仅 `status === 'failed'` 展示，或后端放开并幂等处理。

### P1-10 后端删除版本 projectName 取值错误
- `version.go:368` `projectKey := c.GetString("projectName")`，全仓无任何 `c.Set("projectName", ...)`。
- 影响：非系统管理员删除恒 403；操作日志项目名为空。前端明明传了 `?projectName=`（`delivery.ts:88-90`）。
- 修复：改为 `c.Query("projectName")`（或从 body/路径推导），并做空值校验。

### P1-11 权限与鉴权缺口（后端）
- `GetChartVersionFromRepo`：鉴权被注释，代码中留有 `// TODO: Authorization leak`（`version.go:450-457`），任意登录用户可探测任意 chart 仓库。
- `DownloadDeliveryChart`：只校验系统级 `DeliveryCenter.ViewVersion`，不校验 `projectName` 的项目权限，且 `projectName/version/chartName` 直接拼入后端查询（`version.go:417-429`）。
- `ApplyDeliveryGlobalVariables`：仅系统级 ViewVersion，无项目级校验、无 License 校验（`version.go:558-572`）。
- `CheckDeliveryVersion`：无任何权限与 License 校验（`version.go:584-597`），可被任意登录用户枚举版本名。
- 修复：统一复用 `GetDeliveryVersion` 的项目级 `Version.View/Create` 判定模式，补齐 License。

### P1-12 K8s 版本“秒成功”假闭环（未指定 push 时无任何实际分发）
- 前端 K8s 创建 payload 的 images 只有 `source_image/target_image`，无 `push_image`（`Delivery/index.tsx:367-378`）。
- 后端仅对 `PushImage` 生成分发 workflow（`version_v2.go:255-285`）；无 workflow 时 `checkK8SImageVersionStatusV2:446-449` 直接置 success。
- 影响：版本记录立即显示“已发布/成功”，但镜像并未推送到任何仓库。
- 修复：创建表单暴露 push 开关与目标仓库并写入 `push_image`；或在无分发动作时状态标记为 `manual`，不得显示 success。

## 五、任务书前提与后端实际能力核对

| 任务书描述 | 后端/真理源实际 | 结论 |
|---|---|---|
| 交付物过滤参数 `image, repo_name, branch, commit_id, tag` | Handler 实际读取 `type, image, name, imageTag, repoName, branch, source`；`DeliveryArtifactArgs` 无 `commit_id/tag` 字段 | **前提不准确**；`commit_id/tag` 不支持，repo/branch 走 activity 且丢其它过滤 |

| Helm 全局变量 / Chart 下载 | 全局变量合并会裁掉字段；Chart 下载二进制解析错误 | 均需修复 |
