## 2. 深度审计发现的链路缺陷与对账结果

### 缺陷 LOOP9-A1：系统操作审计日志（Operation Logs）无分页查询、无多维筛选与详情抽屉缺失
- **后端源码真理源**：
  `pkg/microservice/aslan/core/system/handler/operation.go:31-87`：
  - `GET /api/aslan/system/operation` 支持以下查询参数：
    - `username` (string)：操作人员账号过滤；
    - `projectName` (string)：关联项目名过滤；
    - `function` (string)：功能模块过滤；
    - `status` (int)：执行状态（0 为全部，200 为成功，非 200 为失败）；
    - `page` (int, 默认 1)；
    - `per_page` (int, 默认 50)；
  - `pkg/microservice/aslan/core/system/service/operation.go:222-226`：
    ```go
    type FindOperationResponse struct {
        OperationLogs []*models.OperationLog `json:"operation_logs"`
        Total         int                    `json:"total"`
        I18N          *OperationLogI18N      `json:"i18n"`
    }
    ```
  - 单条日志 `models.OperationLog` 包含核心审计线索：`id`, `username`, `product_name`, `function`, `method`, `status`, `created_at`, `request_body`, `targets`, `name`。
- **前端现状缺陷**：
  1. `frontend/src/api/settings.ts` 缺少 `getOperationLogs` 方法与强类型定义；
  2. `frontend/src/pages/Settings/Config/index.tsx` 中审计日志 Tab 写死了固定查询：`http.get('/api/aslan/system/operation?status=0&per_page=50&page=1')`，仅在初次加载拉取一次；
  3. 审计日志 Table 无分页服务端联动，无搜索过滤表单（无法根据操作人员、项目、状态检索）；
  4. 无详情展开/抽屉，审计人员无法查看操作的 `request_body`（请求体）与 `targets`（影响资源目标）。

### 缺陷 LOOP9-A2：用户管理信息编辑入口缺失与列表服务端分页/搜索脱节
- **后端源码真理源**：
  `pkg/microservice/user/core/handler/user/user.go:453-478` 与 `router.go:34`：
  - `PUT /api/v1/users/:uid`：
    ```go
    type UpdateUserInfo struct {
        Name  string `json:"name"`
        Email string `json:"email"`
        Phone string `json:"phone"`
    }
    ```
  - `POST /api/v1/users/search`：接收 `QueryArgs{ name, page, per_page }`，返回 `{ users: UserInfo[], total_count: int64 }`。
- **前端现状缺陷**：
  1. `frontend/src/api/settings.ts` 缺失 `updateUser(uid, payload)` 方法；
  2. `settingsApi.getUsers()` 内部写死 `page: 1, per_page: 200`，未向外暴露分页参数与总数，导致 `UsersPage` 将 `ProTable` 的 `search={false}` 且只能展示本地 200 条，企业级用户量过大时无法翻页与按姓名搜索；
  3. `UsersPage` 用户表格操作列仅有「重置密码」、「重置 MFA」和「删除」，管理员**完全无法编辑修改**用户的显示姓名、工作邮箱与手机号。
