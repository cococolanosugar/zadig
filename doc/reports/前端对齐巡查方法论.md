# 前端对齐巡查方法论

> 适用场景：将一个新实现的前端（如 zadig-portal-next）与一个既有成熟前端的编译产物（如 zadig-ee-portal）做界面与功能对齐。

## 总体框架：三个信息源 × 五层审计 × 三个技巧 × 一个验证闭环

```
信息源（互为校验）
    ↓
L1 路由 → L2 页面功能 → L3 操作能力 → L4 信息密度 → L5 细节深度
    ↓（每层发现 → 修复 → 验证闭环 → 归档）
三个技巧（差分 / 二分 / 契约逆向）
```

## 一、三个信息源（互为校验，缺一不可）

| 信息源 | 获取方式 | 用途 | 局限 |
|---|---|---|---|
| **编译产物逆向** | grep 旧版 `static/js/*.js` chunk | ① 路由全表 ② **中文语言包**（页面名/字段名/按钮文案的权威来源）③ API 路径枚举（grep `"/api/..."` 字符串） | minified；导出名混淆，需按字符串反查 |
| **线上实机走查** | 浏览器 MCP：登录 → 逐页 a11y snapshot / `innerText` 提取 / **网络面板抓包** | 实际渲染的界面元素、交互流程、真实请求序列——验证部署版本的真实行为 | 依赖实例可用性与登录态 |
| **后端源码** | 读 handler：`ShouldBindJSON` 的 Args struct（json tag 逐字段）、`c.Query` 必需参数、license 门控 | 每个端点的请求契约、业务校验、是否需要特定配置（registry 等） | 部署版本可能落后于仓库 HEAD |

**三条纪律**：
1. **三者冲突时以实机实测为准**——部署实例的行为可能与仓库 HEAD 不一致。
2. **下结论前查后端源码**——三次"不可推进"误判（MFA/睡眠唤醒/业务目录真实 API）都源于只看了路由表没确认 handler 是否存在。
3. **语言包是最好的字段字典**——旧版 i18n 的 key（如 `catalog.operators.equals`）直接暴露每个页面有哪些表单字段和操作。

## 二、五层审计法（由粗到细递进）

### L1 路由覆盖
- 从旧产物 chunk 提取路由全表（`path:` 字符串 + 语言包 title）
- 与新 router 逐条做差集；注意**嵌套路由的前缀拼接**（如 `/v1` 下的子路由不带前缀）与**子串误报**（`plugin` 匹配 `plugins`）
- 产出：缺失清单 + "路由存在但渲染占位页"清单（后者同样算缺失）

### L2 页面功能（真实 API vs 占位）
- **特征扫描**：`SAMPLE / demo-service / message.info( / setTimeout...success / 无 onClick 的 Button`
- 每页统计 API 调用数与假数据标记数，形成分级：真实闭环 / 读-only / 假数据兜底 / 纯占位
- 重点甄别"调了 API 但不用返回值"的暗坑（如 fetch 后丢弃，图表用 `Math.sin()` 生成）

### L3 操作能力（写路径）
- 逐个核对后端 router 的写端点（POST/PUT/DELETE）与前端是否有对应 UI
- 契约逆向：Args struct 的 json tag **逐字段**核对，包括必需的 query 参数（`force=true`、`type=k8s`、`reg_provider` 都是实际踩过的坑）
- "两段式"流程（先 GET preset/estimated-values 取渲染好的 body，再 POST 回传）必须完整实现前半段

### L4 信息密度
- 实测列表/详情 API 的响应 JSON，与前端渲染的字段对比
- 典型缺口：后端返回 `recentTasks/isFavorite/successRate` 但前端只渲染名称——旧版列表的信息密度差距就藏在这里

### L5 细节深度
- job 级事件、断点、调试容器、文件下载、服务版本切换
- 状态语义：如环境 `Sleeping` 状态（大写 S）驱动"唤醒"菜单文案

## 三、三个关键技巧

### 1. 差分测试
同一操作在旧 portal 和新前端各执行一次，抓包对比请求。
- 环境创建 500 的根因就是这么定位的：旧 portal 客户端拦截（提示"请选择镜像仓库"）而新前端放行 → 探测发现实例根本没配置 registry
- 旧 portal 页面即使数据为空，其**表单校验规则**（必填项提示）就是后端约束的镜像

### 2. 二分法隔离
500 空响应时先拆变量再试：
- 去掉 services 创建空环境 → 仍 500 → 排除服务渲染
- 验证集群连通性（nodes 列表 200）→ 排除连接问题
- 锁定 registry 缺失 → 配置后 200

### 3. 契约逆向优先于猜测
每个端点动手前先读 handler 源码：
- `ShouldBindJSON` 的 Args struct：json tag **逐字段**核对（`user_name` vs `username`、`is_ssl` vs `isTLS` 都是实际踩过的坑）
- `c.Query` 必需参数：`force=true`（ParseBool 空串报错）、`type=k8s`（决定 body 解析分支）、`production`（权限语义）
- "两段式"流程：preset/estimated-values 先取服务端渲染好的 body，改值后回传

## 四、验证闭环（每个修复批次必过）

```
修复 → tsc -b → vite build → 浏览器走查（读路径）
     → 写路径：创建 → 列表 API 回读确认持久化 → 清理 → 确认归零
```

- 写路径验证必须**回读**确认（创建后用列表/详情 API 查一遍），不能只看 success toast
- 修复真实 bug 后用**重放**验证（如 `force=true` 加上后重放服务创建）
- **环境类陷阱记入持久 memory**，供后续会话与端点接入复用
- 大批量修复分批提交，每批一个主题（便于回溯）

## 五、基础设施陷阱（本项目实测，通用性高）

### 陷阱 1：网关 200+HTML fallback
envoy/nginx 对**未匹配的 API 路径**返回 200 + 旧版 SPA index.html（而非 404）。前端 fetch 会"成功"拿到 HTML。
- **对策**：接任何新端点前先用浏览器 fetch 实测，校验 `Content-Type` 为 JSON 且 body 以 `{`/`[` 开头
- **API 前缀必须实测**：stat 系列在部署实例上是 `/api/aslan/stat/*` 而非源码里的 `/api/stat/*`

### 陷阱 2：部署版本 ≠ 仓库 HEAD
部署实例（EE 5.0.0, commit e441a9c）可能没有仓库 HEAD 新增的路由（如 `/api/stat/dashboard/overview` 曾 404→HTML）。
- **对策**：以后端 handler 源码 + 实机探测双重确认

### 陷阱 3：必填参数的隐性校验
`ParseBool(c.Query("force"))` 对空串直接 400；`reg_provider` 空串被拒——这些校验不体现在 API 文档里，只能从 handler 源码或旧 portal 抓包得知。

### 陷阱 4：实例配置是功能的前置条件
镜像仓库未配置 → 环境创建 panic（空 500）；构建模块缺失 → 工作流触发被业务校验拒绝。旧 portal 的客户端校验规则是这些前置条件的镜像。

## 六、产出与归档纪律

1. **评审记录**：每轮发现/修复/验证归档（评审记录 001 评估、002 执行记录），误判必须在记录中勘误
2. **分层结论**：最终报告按"可对齐（已全部完成）/ 闭源 EE 依赖（明确不做）/ 需实例侧配合"三档收口
3. **持久 memory**：基础设施陷阱写入 memory 供跨会话复用
4. **提交纪律**：分批提交，每批一个主题，message 说明契约来源

## 七、已知残余与判断标准

三层审计 + 界面对比全部闭环后，残余项按如下标准判断是否可推进：

| 判断 | 依据 | 示例 |
|---|---|---|
| **闭源 EE 依赖 → 不做** | 后端端点在开源仓库不存在 | Plutus 子树、SAE 变更单、AI 环境巡检 |
| **旧宿主机制 → 不做** | 依赖旧版前端才能实现的协议 | 微前端插件真正挂载 |
| **需实例配置 → 可解锁** | 端点存在，仅缺配置/数据 | 镜像仓库配置后环境创建恢复 |
| **需实机联调 → 后置** | 前端就绪但需真实运行数据 | 审批流、任务执行全链路 |
