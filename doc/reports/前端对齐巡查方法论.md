# 前端对齐巡查方法论（v2.0）

> 适用场景：将一个新实现的前端（如 zadig-portal-next）与一个既有成熟前端的编译产物（如 zadig-ee-portal）做界面与功能对齐。
> 来源：2026-09 ~ 2026-10 对 Zadig 前端重构的 **40+ 轮巡查、21 个修复批次、65 个提交**实践总结；配套记录见 [评审记录 001](./2026-09-19-评审记录-001.md) ~ [评审记录 010](./2026-10-04-评审记录-010.md)。

## 修订记录（v2.0，相对 v1 的优化）

基于第 3~6 轮暴露的**三处方法性失误**与**四次有效扩展**：

| # | v1 的问题 | v2.0 的修正 | 教训来源 |
|---|---|---|---|
| 1 | 端点枚举只 grep 字面量 `"/api/..."`，**系统性漏掉 `.concat()` 拼接端点**（istioGrayscale/share/bluegreen/manualexec 全族七轮未被发现） | 新增 **L0 枚举与对账**：字面量 + concat 链重建 + **静态段 token 反查** + **注册表整表抽取** | 第三轮 diff "438 vs 303" 看似收敛，实为漏抽 |
| 2 | 缺口清单以散文维护，复检时被**重写**，静默丢项（003 → 006 丢掉 6 项，007/008 宣称 "100% 收口" 是假象） | 新增 **清单与声明治理**：稳定 ID、状态机（gap/fixed/declared/deferred）、每轮 **丢项审计**（上轮 ID 集合 diff） | 第 5 轮靠 token 反查才发现 |
| 3 | "页面存在即对齐"（VMs 页 97 行只读列表、Scanners 硬编码 stub 均被算作完成） | 新增 **操作矩阵 + stub/只读审计**（L2 强化）；残余判定新增"只读/STUB → 必做"档 | 第六轮 G3/G4 |
| 4 | L5 只列"job 事件/断点/调试容器"等散点，漏掉组件级能力（终端工具栏 8 个按钮整组缺失） | L5 新增 **组件级能力对照法**（对每个交互组件列出旧版工具栏按钮集合逐一对照） | 第四轮（批次 17） |
| 5 | 语言包只做"顺手捞"（查个别关键词） | 新增 **语言包全量字典扫描**标准流程：全量标签 → 词表过滤 → 功能名词聚类 → 三点验证 | 第六轮（3825 → 835 → 4 组真缺口） |
| 6 | 抽取器每轮临时重写，前后不可比 | **工具脚本化**：抽取器落库为脚本 + 中间产物留存（`old-endpoints.txt` / `missing-tokens.txt`），跨轮 diff 量化收敛 | 第 3/5/6 轮重复劳动 |
| 7 | 验证只测 happy path | 验证闭环新增 **gating 行为验证**（前置不满足时必须阻断并给出指引）+ **契约自检端点优先**（lint/validate/dryrun 不改数据验证合法性） | 批次 18/19a 的成功验证模式 |

## 总体框架：三个信息源 ×（L0 枚举 + 五层审计）× 六个技巧 × 一个验证闭环

```
信息源（互为校验）
    ↓
L0 枚举与对账（端点 / 路由 / 类型注册表 / 语言包字典）
    ↓
L1 路由 → L2 页面功能 → L3 操作能力 → L4 信息密度 → L5 细节深度
    ↓（每层发现 → 三点验证 → 修复 → 验证闭环 → 归档）
六个技巧（差分 / 二分 / 契约逆向 / 枚举反查 / 验证器优先 / stub 与只读审计）
    ↓
清单治理（稳定 ID · 状态机 · 丢项审计）
```

## 一、三个信息源（互为校验，缺一不可）

| 信息源 | 获取方式 | 用途 | 局限 |
|---|---|---|---|
| **编译产物逆向** | grep 旧版 `static/js/*.js` chunk | ① 路由全表 ② **中文语言包**（字段字典）③ **API 路径枚举**（含 concat 拼接，见 L0）④ **类型注册表**（job types / providers 等） | minified；导出名混淆，需按字符串/token 反查 |
| **线上实机走查** | 浏览器 MCP：登录 → 逐页 a11y snapshot / `innerText` 提取 / **网络面板抓包** | 实际渲染的元素、交互流程、真实请求序列——验证部署版本的真实行为 | 依赖实例可用性与登录态（JWT 约 30~60 分钟过期，需按需重登） |
| **后端源码** | 读 handler：`ShouldBindJSON` 的 Args struct（json tag 逐字段）、`c.Query` 必需参数、license 门控、**job 工厂 switch** | 每个端点的请求契约、业务校验、类型合法性 | 部署版本可能落后于仓库 HEAD |

**三条纪律**：
1. **三者冲突时以实机实测为准**——部署实例的行为可能与仓库 HEAD 不一致。
2. **下结论前查后端源码**——多次"不可推进"误判（MFA / 睡眠唤醒 / 业务目录真实 API）都源于只看了路由表没确认 handler 是否存在。
3. **语言包是最好的字段字典**——旧版 i18n 的 key/value 直接暴露每个页面的表单字段与操作；但须全量扫描 + 过滤 + 聚类（见 §四.5），不要"顺手捞"。

## 二、L0 枚举与对账（v2.0 新增；此前所有重大遗漏的根因都在这层）

> 核心认知：**"上一轮的 diff 收敛" ≠ "枚举完整"**。第 3/6 轮的端点 diff 都因抽取方式缺陷而系统性漏项，导致后续各轮基于错误基线收口。

### 2.1 端点三重抽取（缺一不可）
1. **字面量**：`grep -o '"/api/[a-zA-Z0-9_/.-]*'`；
2. **concat 链重建**：解析 `"prefix".concat(a,"/seg/").concat(b,...)` 链，还原为 `/api/x/{}/seg/{}` 模板（旧包大量端点为拼接构造）；
3. **静态段 token 反查**：把全部路径的静态段（长度≥5 的 camelCase/snake_case）收为 token 集合，反向 grep 新前端——**新前端缺失的 token 即候选**，再逐个三点验证。

### 2.2 注册表整表抽取（比端点更完整的枚举）
旧包中大量功能以**数组/对象注册表**形式存在，一次抽取即可完整对账：
- **job 类型注册表**：`{label:"...",name:"zadig-xxx",type:"zadig-xxx",is_offical:...}`（第 5 轮由此一次性发现 15 类缺失步骤）；
- 其他注册表：集成分类、状态枚举、提供方（providers）、过滤项集合等。
对账方法：注册表与**后端常量表**（如 `config/consts.go` 的 JobType 全集、`controller/job/interface.go` 的工厂 switch）求差集。

### 2.3 路由与菜单
- 旧产物 `path:` 字符串 + 语言包 title；注意**嵌套路由前缀拼接**与**子串误报**（`plugin` 匹配 `plugins`）；
- 差集产出两类清单：路由缺失 + "路由存在但渲染占位页"（后者同样算缺失）。

### 2.4 语言包字典（全量扫描标准流程，见 §四.5）

### 2.5 工具化与留存（v2.0 纪律）
- 抽取器**落库为脚本**（如 `doc/reports/tools/`），不要每轮重写 heredoc；
- 中间产物留存（`old-endpoints.txt` / `missing-tokens.txt` / `missing-l10n.txt`），**每轮重跑 + 与上轮 diff**，量化收敛曲线（缺失数必须单调下降，否则说明抽取退化或清单丢项）。

## 三、五层审计法（由粗到细递进）

### L1 路由覆盖
见 §2.3。产出：缺失清单 + 占位页清单。

### L2 页面功能（真实 API vs 占位）
- **特征扫描**：`SAMPLE / demo-service / message.info( / setTimeout...success / 无 onClick 的 Button`；
- 每页统计 API 调用数与假数据标记数，分级：真实闭环 / 读-only / 假数据兜底 / 纯占位；
- 甄别"调了 API 但不用返回值"的暗坑；
- **（v2.0）操作矩阵**：对每个页面逐项检查 `列表/创建/编辑/删除/批量/导入/导出/行操作/工具栏` 是否具备——**"页面存在 ≠ 功能存在"**；
- **（v2.0）Stub 审计**：grep 创建/更新 payload 中的硬编码默认值（固定 `timeout: 600`、`hook_ctl:{enabled:true,items:[]}`、空数组、`|| 0`），凡"能打开能提交但能力丢失"的 stub 一律计入缺口。

### L3 操作能力（写路径）
- 逐个核对后端 router 的写端点（POST/PUT/DELETE）与前端是否有对应 UI；
- 契约逆向：Args struct json tag **逐字段**核对，包括必需 query 参数（`force=true`、`type=k8s`、`reg_provider`、`production` 都是实际踩过的坑）；
- "两段式"流程（preset/estimated-values 先取再回传）必须完整实现前半段；
- **（v2.0）类型合法性**：凡涉及枚举类型（job type / scanner type / medium type），必须与后端常量表对齐——曾有 palette 写入非法 `helm-deploy` 被后端 lint 拒绝。

### L4 信息密度
- 实测列表/详情 API 响应 JSON 与前端渲染字段对比；
- 典型缺口：后端返回 `recentTasks/isFavorite/successRate` 但前端只渲染名称；
- 列表列头差分（旧 Element UI `.el-table__header` vs 新 antd `.ant-table-thead` 并排对照）。

### L5 细节深度
- job 级事件、断点、调试容器、文件下载、服务版本切换、状态语义（`Sleeping` 驱动"唤醒"文案）；
- **（v2.0）组件级能力对照法**：对每个交互组件（终端 / YAML 编辑器 / 日志查看器 / 文件树 / DAG 画布 / 表格），从旧包提取其**工具栏按钮全集**（l10n key 组）逐一对照——终端工具栏（下载/搜索/清屏/重连/跳顶底/复制/全屏）整组缺失 7 轮后才被发现，即因此缺口而漏。
- 环境高级能力清单：自测模式（共享/基准环境）、Istio 灰度发布、共享存储/缓存/调度策略等**常驻"深水区"清单**。

## 四、六个关键技巧

### 1. 差分测试
同一操作在旧 portal 和新前端各执行一次，抓包对比请求。
- 环境创建 500 的根因就是这么定位的：旧 portal 客户端拦截（"请选择镜像仓库"）而新前端放行 → 探测发现实例根本没配置 registry；
- 旧 portal 页面即使数据为空，其**表单校验规则**就是后端约束的镜像；
- 列表页并排对照（列头/按钮集合）比逐页读代码快得多。

### 2. 二分法隔离
500/空响应时先拆变量再试：去掉 services 创建空环境 → 仍 500 → 排除服务渲染；验证集群连通性 → 排除连接问题；锁定 registry 缺失 → 配置后 200。

### 3. 契约逆向优先于猜测
每个端点动手前先读 handler 源码：json tag 逐字段（`user_name` vs `username`、`is_ssl` vs `isTLS`）；`c.Query` 必需参数；"两段式"流程。**（v2.0）同时读 job 工厂 switch 与常量表**，确认类型合法性与实现存在性。

### 4. 枚举反查（v2.0 新增）
不正向找"旧版有、新版没有"，而是**把旧包的全部静态段 token / 注册表条目作为探针**，反向 grep 新版：
- token 缺失即候选（第 5 轮一次挖出 istioGrayscale/share/canary/manualexec 全族）；
- 注册表差集即功能差集（job types 40 vs 11 → 15 类缺失）；
- 优点：不依赖"路径模板能完全还原"，容错 minified 的任意构造方式。

### 5. 验证器优先（v2.0 新增）
后端提供的**自检端点**是零成本的契约验证器，优先于创建真实数据：
- `POST /api/aslan/workflow/v4/lint`（job type 合法性，`helm-deploy` → 400 实证 bug、合法类型 → 200）；
- `PUT /service/services/yaml/validator`、各类 `check/*/ready`、`*/validate`；
- 用法：批量改造类型/payload 后先过 lint/validate，再进实机 E2E。

### 6. Stub 与只读审计（v2.0 新增）
页面"能用"有三种假象，均须显式排查：
| 假象 | 检测 | 案例 |
|---|---|---|
| **只读列表** | 页面行数/操作列按钮数骤少 | VMs 页 97 行纯列表（旧版有接入/离线/恢复/升级） |
| **硬编码 stub** | create/update payload 常量扫描 | Scanners 创建 `hook_ctl:{items:[]}` 写死 |
| **占位渲染** | L2 特征扫描 | 历史 SAMPLE_PODS 等 |

## 五、验证闭环（每个修复批次必过）

```
修复 → tsc -b → vite build → antd lint（0 废弃项）
     → 实机走查：读路径 + 写路径（创建 → 回读确认持久化 → 清理 → 确认归零）
     → gating 验证：前置不满足时必须正确阻断并给出指引（v2.0）
```

- 写路径验证必须**回读**（创建后用列表/详情 API 查一遍），不能只看 success toast；
- **自建自清**为硬性要求：验证数据一律创建后删除，实例零残留（如临时环境 `dl-verify`、`test-group-21b`、`test_vm_probe`）；
- **（v2.0）gating 验证**：不只测 happy path——实例缺 Istio 时灰度开关必须阻断并给安装指引；非生产环境调灰度必须 400；这是"功能正确"的一半；
- 修复真实 bug 后**重放**验证；大批量修复分批提交，每批一个主题（message 说明契约来源）。

## 六、清单与声明治理（v2.0 新增）

### 6.1 缺口台账（稳定 ID + 状态机）
- 每个缺口分配**稳定 ID**（如 `G1/A2/C1`），清单**只增不删**；
- 状态机：`gap → fixed（commit 号）| declared（不做）| deferred（延后，附理由与排期）`；
- 状态迁移必须附证据（提交号 / file:line / 实测记录），不接受"应该差不多"。

### 6.2 丢项审计（每轮必做）
- 新轮次生成清单前，先 diff **上轮 ID 集合**：消失的 ID 必须显式说明去向（fixed/declared/deferred），否则视为丢项事故；
- 教训：003 → 006 重写清单静默丢掉 6 项（manualexec/custom_workload/canary_service/capacity/system-language/release_plan-hook），导致两个轮次宣称假性收口。

### 6.3 声明集（declared）的证据标准
每条声明必须带：**依据类型**（后端无端点 / 实例移除 / 无 UI 消费证据 / 等价覆盖）+ **证据**（file:line / grep 结果 / 实机响应）+ **复检方式**：
- "等价覆盖"必须给出替代路径（如 `itreport` → testtask 详情 + JUnit 报告；`extractVariable` → 保存时后端自动提取 templatestore yaml.go:706）；
- 声明集不是"免检区"：每轮 token 反查自动复验一遍，误判需勘误（`validateUpdate` 即从"待实现"修正为"后端不存在，改用 yaml/validator"）。

### 6.4 收敛度量（何时可以说"无已知缺口"）
三项指标同时满足才可宣布：
1. token 反查缺失数 = 0（或全部落入声明集）；
2. 注册表差集 = 0（或全部 declared）；
3. 语言包功能级缺失聚类全部三点验证完毕（gap 或 declared）。

## 七、域轮转清单（v2.0 新增）

避免"总查熟悉域"，按下表轮转，每轮至少覆盖 2 个历史薄弱域：

`路由/布局 | 环境(K8s/Helm/VM) | 工作流(编排/执行/触发器) | 服务/构建/测试/扫描/制品 | 集群/主机/存储 | 系统设置/集成 | 权限(用户/用户组/RBAC) | 目录/模板 | 洞察/统计 | 发布计划/迭代`

- 经验：集群配置（调度策略/缓存/共享存储）与用户组管理直到第六轮才被覆盖；
- 端点常**跨域**（同一功能横跨 env+workflow+system），故须配合 §2.1 的 token 反查做"功能族"级检查。

## 八、基础设施陷阱（本项目实测）

### 陷阱 1：网关 200+HTML fallback
envoy/nginx 对**未匹配的 API 路径**返回 200 + 旧版 SPA index.html。接任何新端点前先用浏览器 fetch 实测，校验 `Content-Type` 为 JSON 且 body 以 `{`/`[` 开头。API 前缀必须实测（stat 系列在实例上是 `/api/aslan/stat/*`）。

### 陷阱 2：部署版本 ≠ 仓库 HEAD
实例可能没有仓库 HEAD 新增的路由。以后端 handler 源码 + 实机探测双重确认。

### 陷阱 3：必填参数的隐性校验
`ParseBool(c.Query("force"))` 对空串直接 400；`reg_provider` 空串被拒——只能从 handler 源码或旧 portal 抓包得知。

### 陷阱 4：实例配置是功能的前置条件
镜像仓库未配置 → 环境创建 panic；集群未装 Istio → 灰度开启必失败（业务层 500 `failed to ensure EnvoyFilter`）。旧 portal 的客户端校验规则是这些前置条件的镜像；**验证这类功能时 gating 行为本身就是验收项**。

### 陷阱 5：登录态时效（v2.0 新增）
实例 JWT 约 30~60 分钟过期，长巡查中途会整页落回 `/signin`（新旧 portal 均如此）。对策：批量实机脚本内先探测 `GET /environments` 是否 200，401 则自动重登再继续；会话掉线不要误判为"页面 bug"。

### 陷阱 6：旧包体结构差异（v2.0 新增）
路由表/端点的字面量形态随 chunk 而异（Vue Router 数组、`concat` 拼接、注册表对象）。任何"抽取结果比预期少"都应先怀疑抽取方式，而不是直接下"旧版没有"的结论——**抽取器要交叉验证**（字面量 vs 反查 token 的差集）。

### 陷阱 7：执行端会话网络中断（v2.0.1 新增，实战）
派发批次执行中途可能因网络中断（终端显示 `There was a network issue connecting to the server` + Error ID）静默中断本轮回复。
- **处置**：① `git status` + `git log` 确认是否有半成品或已提交改动；② 无改动 → 重发续跑指令（附错误 ID + 批次要点）；③ 半成品 → 先让其自查现状再续；④ 监督脚本加入 `network issue` 探测（出现即中断轮询并上报，避免 60 分钟空等）；⑤ 长批次（>30 分钟）预期需要"重启续跑"路径。

## 九、产出与归档纪律

1. **评审记录**：每轮发现/修复/验证归档（001 评估、002 执行记录……），误判必须在记录中勘误；
2. **分层结论**：最终报告按"可对齐（已全部完成）/ 闭源 EE 依赖（明确不做）/ 需实例侧配合"三档收口；
3. **持久 memory**：基础设施陷阱写入 memory 供跨会话复用；
4. **提交纪律**：分批提交，每批一个主题，message 说明契约来源；
5. **（v2.0）批次执行模板**：派发修复批次时必须包含 ①契约 file:line ②验收标准（tsc/build/lint 0 废弃 + 实机自建自清）③汇报格式（表格：项 | 契约 | 状态 | 实测）；派发后必须确认"已提交执行"（仅输入未回车的事故发生过）；
6. **（v2.0）独立复核**：关键类型/端点不信任前端自测，用后端常量表与工厂 switch 二次核对。

## 十、已知残余与判断标准

| 判断 | 依据 | 示例 |
|---|---|---|
| **闭源 EE 依赖 → 不做** | 后端端点在开源仓库不存在 | Plutus 子树、SAE 变更单、AI 环境巡检、MSE 灰度 |
| **旧宿主机制 → 不做** | 依赖旧版前端才能实现的协议 | 微前端插件真正挂载 |
| **后端无端点 → 不做** | 旧 UI 文案存在但开源后端无对应 handler | 项目类型切换（托管）、API Token 权限开关、镜像名称策略 |
| **只读 / STUB → 必做**（v2.0） | 端点存在且旧版有写操作，新版仅只读/硬编码 | VMs 操作、扫描高级设置、集群配置三项 |
| **需实例配置 → 可解锁** | 端点存在，仅缺配置/数据 | 镜像仓库配置后环境创建恢复；集群装 Istio 后灰度/自测可用 |
| **需实机联调 → 后置** | 前端就绪但需真实运行数据 | 审批流、任务执行全链路 |
